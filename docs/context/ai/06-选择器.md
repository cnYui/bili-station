# P4：选择器与自然语言删除

## 不是新机制

`sort --engine external` 那套（4260 条实战验证过的）已经是正确答案：
CLI 吐清单 → 调用方裁决 → CLI 校验后落地。P4 只是把它从「分类」抬成通用能力。

> **任何批量操作 = 选择器 + 动作。**
> 选择器有三个来源：声明式过滤 / 显式 id 列表 / **外部裁决**。

自然语言删除就是第三种来源，不需要任何新机制。

## 流程

```bash
# 1. CLI 吐候选清单（带证据字段）
node cli.mjs follow remove --inactive-days 365 --emit-candidates cand.json

# 2. 你 / agent / 自然语言裁决，写成 {"selected": {"<id>": "<理由>"}}

# 3. 回填，CLI 校验
node cli.mjs follow remove --apply picked.json          # 干跑看结果
node cli.mjs follow remove --apply picked.json --yes    # 确认后执行
```

## 比分类多的两条护栏

删除比分类狠，所以 `applySelection` 比 `applyExternalAssignment` 多两条：

### ① 回填必须带理由

格式从 `{id: 分类名}` 变成 `{id: "理由"}`。空理由直接拒收（`NO_REASON`）。

**理由会写进备份文件。** 自然语言的判断依据无法从结果反推——不记下来，
一个月后看备份只剩一堆 id，完全不知道当初为什么删。

### ② protected 是数据结构层的硬护栏

受保护对象（特别关注、指定分组）在候选清单里就标 `protected: true`，
回填若选中它们一律拒收（`PROTECTED`）并计数。

**靠结构挡，不靠提示词挡。** 提示词会被忽略，数据结构不会。
要动必须显式 `--allow-protected`。

## 拒收分类

| code | 含义 |
|---|---|
| `NOT_IN_CANDIDATES` | 不在候选清单里（凭空冒出来的 id） |
| `PROTECTED` | 受保护对象，需要 `--allow-protected` |
| `NO_REASON` | 没给理由 |

超过 `--max-select` 时**整份拒绝而不是截断**——截断会让调用方
以为全做了，是比报错更坏的失败模式。

## 证据字段：确定性判断 vs 语义判断

候选清单里每个对象带的证据决定了裁决方能判断什么。**先分清哪些问题根本不需要语义。**

| 问题 | 该用什么 |
|---|---|
| 「一年没更新的」 | **确定性过滤**，`unfollow --only-inactive --inactive-days 365`。有 `lastPubTs` 就能精确算，交给模型只会引入错误 |
| 「投稿数为 0 的僵尸号」 | 确定性，`count === 0` |
| 「内容转型了」「全是恰饭」「和我关注的方向无关」 | **语义裁决**，需要 `recentVideos` 里的标题和简介 |

所以候选清单里同时给两类字段：

```jsonc
{
  "uploadCount": 120,
  "lastPubTs": 1789534800,
  "daysSinceLastPub": 517,        // 天数直接算好 —— 让裁决方做日期运算是白白制造出错机会
  "recentVideos": [               // 语义判断的核心证据，没跑 scan uploads --videos 时为空
    { "title": "...", "desc": "...", "publishedAt": 1789534800 }
  ]
}
```

没有 `recentVideos` 时清单的 `note` 会明说「只能按停更时长这类硬指标判断」，
避免裁决方硬猜内容。

## 投稿数据的成本结构

`/x/space/wbi/arc/search` 的关键性质：**拿 1 条和拿 20 条是同一次请求**。
成本只跟 UP 主个数走。

```
scan uploads --videos 0    只要最后投稿时间
scan uploads --videos 5    默认，够做语义判断
scan uploads --videos 20   调用次数完全一样，只是响应大一点
```

5000 个关注 ≈ 5000 次请求 ≈ 85–100 分钟。只读操作，权重 0.05，
边查边存（每 25 个落盘），中断重跑会接着查。

已有记录但视频条数不够时会**自动重查**——否则先跑 `--videos 0` 再跑 `--videos 5`
会被「已缓存」全部跳过。

## 选择文件格式

```json
{
  "v": 1,
  "kind": "unfollow",
  "createdAt": "...",
  "query": "取关一年没投稿的技术区UP，但保留特别关注",
  "instruction": "...",
  "constraints": { "maxSelect": 200, "protectedCount": 42, "reasonRequired": true },
  "candidates": [
    { "id": "1001", "uname": "...", "state": "normal", "tags": ["编程"],
      "followedAt": 1700000000, "lastPubTs": 1650000000, "uploadCount": 12,
      "sign": "...", "protected": false }
  ]
}
```

`query` 字段存原始自然语言，是审计链的起点：
**原话 → 候选清单 → 逐条理由 → 备份文件**，每一环都可回溯。

## 不能松的一条

**选择器永远不直接执行。** 它只产出候选集，仍然要过：

1. `--yes` 闸门（默认干跑）
2. 干跑预览（打印将要动的对象和理由）
3. 执行前备份（含理由）

「AI 已经判断过了」恰恰是**更该留闸门**的理由，不是放宽的理由。

## 框架接法

`defineCommand({ selectable: true })` 自动注入
`--emit-candidates` / `--apply` / `--max-select` / `--allow-protected`，
和 `mutating: true` 注入 `--yes` 完全同构。

目前 `follow` 勾了这个开关。`dead` 也该勾（「让 AI 挑哪些失效视频值得留」），
但失效视频的判断是机械的，暂时没这个需求。
