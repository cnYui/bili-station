# P1.5：探针实测结论

**这份文档是全套里最重要的一份。** 下面每条都是在真实账号上跑出来的，
不是从文档抄的、也不是推测的。两条推翻了原本的设计假设。

结果落在 `~/.bili-station/probes.json`，命令读它来决定行为。重测：

```bash
node cli.mjs probe fav-order --yes
node cli.mjs probe relation-act --yes
node cli.mjs probe list            # 看已有结论
```

## 为什么要有探针

B 站的行为不可靠且没有权威文档。这个项目一贯的原则是**先验和证据冲突时信证据**
（热度模型那次教训）。探针把「花极小代价换确定性」变成一类一等公民命令：
几次写操作换来一个确定结论，比把猜测硬写进代码强得多。

## probe fav-order（2026-09-20 实测）

样本：「生活」夹，逐条 copy 3 条 + 整批 copy 3 条，回读对比。

| 问题 | 结论 |
|---|---|
| **Q1** copy/move 之后 `fav_time` 保留还是重写？ | **重写成操作时间** ✓ |
| **Q2** 同一次调用里的条目 `fav_time` 是否相同？ | **完全相同** ✓ |
| **Q3** 先提交的排在前还是后？ | **排在后** ✓ |

三条合起来印证了 `src/order.mjs` 顶部的推导：

> **提交顺序的逆序 = 最终显示顺序。想让某条排最前，就得最后提交它。**

Q2 决定了**排序精度上限就是一批**（默认 20 条）。要逐条精确只能
`--chunk-size 1`，代价 20 倍调用次数。

探针用的是 `copy` 不是 `move`，所以来源夹完全不受影响。跑完会清空探针夹
（夹本身留着，叫 `_probe_排序探针`，可手动删）。

## probe relation-act（2026-09-20 实测）

样本：一个已关注、非特别关注的 UP。**全程保持关注状态**，不新关注、不取关，
临时分组用完即删。

| 问题 | 结论 |
|---|---|
| `setUserTags` 是覆盖还是追加语义？ | **覆盖** ✓ |
| 特别关注（tagid -10）能通过分组接口写入吗？ | **不能** ✗ code=22117 |
| act=1（关注）有效吗？ | **有效** ✓（22014 是语义拒绝，不是接口不认） |
| act=3（悄悄关注）有效吗？ | **无效** ✗ code=-400 |
| act=2（取关） | 早就实测过，有效 |

### 推翻的假设一：特别关注可读不可写

`/x/relation/tags` **会**把 `tagid=-10「特别关注」` 连同 count 一起列出来，
`tagUsers(-10)` 也能正常读出 42 个成员。所以读这条路是通的。

**但 `setUserTags(mid, [-10])` 返回 22117**，写不进去。

这个非对称性很反直觉——列表里有它、能读它，就是不能通过这个接口写它。
原因未定（可能接口不支持，也可能是特别关注人数配额）。

**已经做的处理**：`follow set --state special` 直接拦下并说明原因，
而不是发一个注定失败的请求。目前只能到网页端手动设置。

**后续要查的**：B 站网页端设置特别关注时到底调什么接口。查清楚之后加一个
探针验证，再放开这条路径。

### 推翻的假设二：悄悄关注（act=3）不可用

`-400 请求错误`。可能已下线，也可能需要额外参数。
`follow add/set --state quiet` 同样直接拦下。

### 为什么 22014 是「可用」而不是「不可用」

第一版探针把 `code !== 0` 一律判成不可用，于是把
`22014 已经关注用户，无法重复关注` 误判成「act=1 不可用」。

**收到这个错误恰恰证明接口认得这个动作**——它是语义拒绝（前置条件不满足），
不是「不认识这个 act」。所以探针现在有一层 `classifyActCode()`：

```
code === 0      → 可用
code === 22014  → 可用（act 有效，只是样本已处于该状态）
code === -400   → 不可用（act 值不被接受）
code === -101/-111 → 结论无效（登录态问题）
```

### 探针自身踩过的坑：空真导致的假阳性

第一版验证覆盖语义的做法是「加进特别关注 → 再移出 → 看移出成功没」。
但**加进去那一步本身失败了**，于是「移出成功」是空真，探针报了
`✓ setUserTags 确实是覆盖语义` —— 假阳性。

**现在每一步都先断言前置条件成立**，不成立就标 `结论无效` 而不是继续往下判。
`fmt()` 有三态：`是 / 否 / 结论无效`。

写探针时这是最容易犯的错：**验证「移除」必须先确认「添加」成功**。

## 命令如何消费探针结果

`src/cli/commands/follow.mjs` 的 `checkSupport(state)`：

- probes.json 里**没有**记录 → 只警告不拦（提示去跑探针）
- 有记录且明确不可用 → **直接拦下**，错误信息里带 code、实测时间、重测命令

原则：静默失败比报错难查得多。宁可拦住，也不发一个注定失败的请求。
