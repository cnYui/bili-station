# P2：排序

## 问题

用户的收藏按时间从新到旧，但重新分类进新夹之后，**最新收藏的反而排在最底**，
必须翻到底或切换成时间倒序才看得到。

## 根因（四个环节，全部在代码里确认过）

| 环节 | 位置 | 行为 |
|---|---|---|
| 读取 | `bili.mjs` `favItems` 用 `order=mtime` | 数组是**新→旧** |
| 计划 | `plan.mjs` `planFavClassify` | 只排序分类，**条目顺序原样保留** |
| 分块 | `executor.mjs` `buildFavOps` | 按数组序切 20 条一批 → **最新的最先提交** |
| B 站 | — | 按 `fav_time` 降序显示，而 move/copy **重写 `fav_time`** |

最先提交的那批拿到最早的新时间戳，于是原本最新的收藏沉到了最底。

最后一环是 `probe fav-order` **实测确认**的，不是推测。详见
[03-探针实测.md](03-探针实测.md)。

## 唯一要记住的规律

> **提交顺序的逆序 = 最终显示顺序。想让某条排最前，就得最后提交它。**

这句话写在 `src/order.mjs` 顶部。改排序相关代码前先读那段推导。

## `--order`（按结果命名，不按机制命名）

```
--order original    新夹里最近收藏的排最上面（和原来一致）   ← 默认
--order reverse     新夹里最早收藏的排最上面
--order pubdate     按视频投稿时间排
--order as-scanned  重构前的行为（复现旧结果、回归测试用）
```

`original` 的实现是**按 `favTime` 升序提交**——每个分支都是「想要的显示顺序」的逆序。
这一点容易看反，`orderItems()` 每个 case 上都写了注释。

`original` 现在是默认值。重构前的行为等价于 `as-scanned`，想要旧行为得显式指定。

## 三个硬约束

### ① 精度只能到一批

实测 Q2：同一次调用里的条目 `fav_time` **完全相同**。所以排序精度上限就是
`--chunk-size`（默认 20）。要逐条精确就 `--chunk-size 1`，代价是 20 倍调用次数
（3808 条 → 3808 次）。只适合小夹精修。

### ② 多来源夹会打断全局顺序

`moveResources` 要求单一 `src_media_id`，所以全局按时间排完还得在来源边界断开：

```
--order-scope per-source   每个来源夹内部有序，调用次数不变        ← 默认
--order-scope global       全局严格有序，来源交错处产生碎块
```

干跑摘要会直接打印 `调用次数 265 → 290`，由用户自己权衡，不替他决定
（`orderCost()` 就是干这个的）。

**先 merge 成单一来源时这个约束不触发**——那正是上次 4260 条实战的做法。

### ③ 碎块变多 = 更容易撞单轮 100 次上限

调用次数上升意味着要多拆一轮。这条也进摘要。

## 实现位置

- `src/order.mjs` —— `orderItems` / `chunkBySource` / `orderCost`，纯函数，可单测
- `src/executor.mjs` —— `buildFavOps` / `buildMergeOps` / `buildDeadOps` 接受
  `order` / `orderScope` / `chunkSize`
- 注册表的 `ordered: true` 能力开关自动注入这三个 flag

`buildFavOps` 用 `chunkBySource`（它要混合多个来源）；`buildMergeOps` /
`buildDeadOps` 的 src 已经按组固定，只需要组内 `orderItems` + 普通 `chunk`。

## 一个必须知道的副作用

**改 `--order` 会让断点文件失效。** op 的 key 是
`mv:<src>:<分类>:<id1>_<id2>...`，重排之后同一批里的 id 组合变了，
断点记录的 key 对不上，已完成的操作**不会被跳过**。

这是合理的——不同的批次划分本来就是不同的操作。但跑到一半改排序要有心理准备。

## 向后兼容

`orderItems` 在条目没有 `favTime` 时按原始下标做稳定回退，所以：

- 假后端的测试数据（没有时间戳）顺序不变 → `test-sort-flow.mjs` 59 条全绿
- 旧缓存里没有 `favTime` 的条目不会被打乱
