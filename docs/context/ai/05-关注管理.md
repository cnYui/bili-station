# P3：关注管理

## B 站的关系模型是三个正交维度

命令设计必须照着它来，否则会出现「改了分组把特别关注弄掉了」这种事。

| 维度 | 取值 | 底层实现 |
|---|---|---|
| 关注状态 | 未关注 / 普通 / 悄悄 / 拉黑 | `/x/relation/modify` 的 `act` |
| **特别关注** | 是 / 否 | **就是 `tagid = -10` 的分组** |
| 普通分组 | `tagid` 0..N | `/x/relation/tags/*` |

**维度 2 和 3 共用同一套 API**，所以绝不能做成两套命令。
证据是现成的：`specialFollowings()` 读的就是 `tagid=-10`，而
`/x/relation/tags` 会把「特别关注」和用户自建分组一起列出来。

## 命令族（面向状态，不面向动词）

```
follow list    [--tag 编程] [--state normal|special|quiet] [--inactive-days 365] [--limit N]
follow add     <uid...> [--state normal|quiet] [--tag 编程]
follow remove  <uid...>                              # 取关，也支持选择器
follow set     <uid...> --state special|normal|quiet
follow tag create|rename|delete <名称>
follow tag add|remove <分组> <uid...>
```

`unfollow` 保留为独立命令（旧 flag 全部兼容），不是 `follow remove` 的别名——
它有自己的规则式筛选（`--keep` / `--inactive-days` / `--only-inactive` / `--protect-tag`），
和 `follow remove` 的「显式列表 / 选择器」是两种不同的用法。

## `setUserTags` 是覆盖语义

**实测确认**（见 [03-探针实测.md](03-探针实测.md)）：传进去的 `tagids`
就是该用户之后的**全部**分组。

所以「把某人加进分组 X」的正确做法是：

```js
const cur = new Set(tagsOf(u, special));   // 读出他现在的全部分组
cur.add(Number(targetTagId));              // 加上目标
setUserTags([mid], [...cur]);              // 传完整集合
```

**只传 `[targetTagId]` 会把他原有的分组和特别关注一起抹掉。**
`buildUserTagOps` 接受的就是「完整目标集合」而不是「要加的那个」，
并且会把目标集合相同的 mid 合并成一批发送。

「移出某个分组」同理 = 传「除它以外的其余分组」。没有 removeUsers 接口。

## tagid 必须自己校验

**B 站对不存在的 tagid 返回 `code 0 "OK"`**（实测 `tagids=999999999`）。
配合覆盖语义，传错 id 不报错，只会把这个人原有的分组**静默清空**。

`validateTagIds(desired, tagById)` 在发请求前校验所有目标 tagid 是否在已知分组里
（`-10` / `0` 例外）。这道校验不能省，它挡的是最难查的一类失败。

## 目前受限的两条路

| 想做的事 | 状态 | 表现 |
|---|---|---|
| `--state special` | **配额预检**（不硬拦） | 22117 的 message 是「特殊关注达到上限」——写入路径通的，是名额满了。腾出名额即可用 |
| `--state quiet` | **拦下** | `/x/relation/modify act=3` → -400「请求错误」 |

`checkSupport(state)` 读 `probes.json` 决定拦不拦：

- 没有探针记录 → 只警告，提示去跑 `probe relation-act`
- 有记录且明确不可用 → 直接拦下，错误信息带 code、实测时间、重测命令

**原则：静默失败比报错难查得多。** 宁可拦住，也不发一个注定失败的请求。

这两条路径的代码是写好的，一旦探针证明接口可用（或找到正确的接口），
把 `checkSupport` 放开即可，不用重写命令。

## 风控权重

`risk.mjs` 的 `OP_WEIGHT` 新增了三项：

```js
follow: 1.4,      // 关注比取关更敏感：批量关注是典型的养号行为特征
quietFollow: 1.4,
tagEdit: 1.2,     // 建/改/删分组是账号结构变更，比往分组里塞人重
```

关系变更**每个 mid 单独成 op**——接口没有批量形式，而且权重高，逐个做才好控速。
分组归属（`tagAdd`）可以一次塞 20 个 mid。

## 护栏

**默认永不动特别关注。** 这条从 `unfollow` 提升成了全族默认：

- `follow remove <特别关注的uid>` → 直接报错，要动必须显式 `--allow-protected`
- 选择器的候选清单里，特别关注被标 `protected: true`，回填选中即拒收
- `unfollow` 的 `--protect-tag` 可以把任意分组也纳入保护

## 数据装载

`src/cli/followdata.mjs` 统一负责：

```js
loadFollowData(ctx, { refresh, needUploads })
  → { list, total, truncated, special: Set, tags, tagById, uploads, warnings }
```

- 关注列表拉一次要两分钟（5000 个），默认用 `followings.json` 缓存
- `truncated` 会进 warnings —— B 站的分页深度限制，不是 bug
- `needUploads` 且 `uploads.json` 为空时给出明确提示（指向 `scan uploads`），
  而不是静默命中 0 个目标
