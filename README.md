# B 站本地整理台

**中文** · [English](README.en.md)

本地运行的 B 站账号整理工具，带可视化页面。关注清理 / 关注分组 / 收藏夹分类 / 失效视频清理。

**所有写操作都经 CDP 在你已登录的 Chrome 页面里发出**，请求带完整浏览器指纹（buvid3/4、bili_ticket、Sec-Fetch-*），
而不是本地进程自己拼 Cookie + 手写 UA。这是读完 12 个同类开源项目后得出的关键结论：指纹残缺是纯 CLI 工具
不得不把退避做到 60s 起步的根本原因。

零运行时依赖，只用 Node 内置模块。需要 Node ≥ 22。

## 两种用法

**CLI（推荐，也便于让 Claude / Codex 代劳）**

```bash
npm run chrome                  # 开带调试端口的 Chrome，在里面登录 B 站
npm link                        # 注册全局 bili-station 命令（或直接 node cli.mjs）

bili-station status
bili-station sort --folders "编程开发,游戏,美食烹饪,科普知识"    # 吐出待分类清单
bili-station sort --folders "编程开发,游戏,美食烹饪,科普知识" --assign assign.json        # 干跑看计划
bili-station sort --folders "编程开发,游戏,美食烹饪,科普知识" --assign assign.json --yes  # 执行
```

核心约束：**候选收藏夹由你定，分类器只能从候选里选唯一一个，不允许发明新分类。**
这样配额溢出在设计上就不可能发生。流程是：定候选 → 缺的先建出来 → 把候选名单交给分类器 →
按标题 / UP / 简介路由 → 按批复制或移动。

### 分类由谁来做

默认 `--engine external`：**CLI 只吐清单，分类由调用方给出，不需要任何 API key。**
如果调用你的就是 Claude / Codex，它本身就是 LLM，再外挂一个模型既多一把 key 又多一份钱。

```bash
bili-station sort --folders "A,B,C" --emit-tasks tasks.json
# 读 tasks.json，给每条选一个 candidates 里的分类，产出 {"<视频id>":"<分类名>"}
bili-station sort --folders "A,B,C" --assign assign.json --yes
```

不在候选集里的分类会被**拒收**而不是静默乱放（收藏夹放错了很难发现），
结果里的 `rejected` 会告诉你拒了几条、分别是什么。

其他两种引擎：
- `--engine keyword` 本地关键词规则，不联网不花钱
- `--engine deepseek` CLI 自己调模型，需要自备 `DEEPSEEK_API_KEY`（仓库不预置任何 key）

### 给 agent 调用

加 `--json`：stdout 只有一个 JSON 对象，日志走 stderr。
退出码有语义：`0` 成功 / `1` 错误 / `2` 风控中止 / `3` 登录失效 / `4` 无事可做。
仓库里的 [AGENTS.md](AGENTS.md) 是写给 agent 读的操作规程。

`bili-station --help` 有完整选项。

## 风控引擎

把 12 个同类项目里各自只做对一半的做法合成一套：

| 机制 | 来源 |
|---|---|
| 错误码语义分流：风控码退避重试，登录码立刻停 | bili-unfollow |
| 衰减滑窗热度模型（45 分钟半衰期，green/yellow/orange/red） | bilibili-following-manager 的「风控日历」 |
| AIMD 快降慢升：撞限流延迟翻倍 + 全局冷却；连续 5 次成功 ×0.85 | Bilibili-AI-Favorites-Organizer |
| 单轮写操作硬上限 100 | following-manager（社区实测 500+ 无延迟几乎必风控） |
| 随机抖动而非固定节奏 | bilibili-unfollow（固定 250ms 本身就是机器特征） |
| 撞墙即停而非硬闯 | bilibili-unfollow |

不同写操作按敏感度加权，**新建收藏夹权重最高（2.5×）**，因为连续建夹最容易触发。

## 补上了同类项目普遍漏掉的几个坑

- **关注列表分页上限**：12 个项目全都把「接口读不到了」当成「已经读完了」。本工具会把 `truncated` 标出来并告诉你只读到多少。
- **收藏夹配额预检**：配额满时 B 站返回的错误长得像限流，极易误判为风控。计划阶段就预先算好会不会超。
- **单夹 1000 条上限预检**：提前告诉你哪个夹会溢出、溢出几条。
- **同名夹复用**：精确匹配 → 忽略大小写与首尾空格。重跑不会建出「游戏_1」「游戏_2」。
- **建夹幂等按存在性判断**，而不是靠断点记录。断点说建过了但夹其实不在（被手删 / 建到一半失败）时，不会导致后续移动全部落空。
- **新建夹默认私密**（`privacy=1`），分出来的几十个夹不会挂在你主页上。设置里可改。

## 安全网

- 所有破坏性操作默认**干跑**，界面上要显式取消勾选才会真执行
- 真执行前自动快照备份到 `~/.bili-station/backups/`，带时间戳，永不覆盖
- 断点续跑：已完成项记在 `resume-*.json`，重跑自动跳过
- 特别关注**无条件保留**，不受任何规则影响
- 收藏夹分类建议先用**复制模式**确认结果，再切移动模式（复制可逆，移动不可逆）
- API Key 只存本地配置，不进任何导出或备份；接口返回里也做了打码

## AI Key

**默认路径不需要任何 key**，仓库里也不预置。
只有显式用 `--engine deepseek` 时才需要，优先级：`DEEPSEEK_API_KEY` 环境变量 > `~/.bili-station/config.json`。
配置文件在仓库之外，不会被提交；接口返回和导出里都做了打码。

## 一次真实规模的实测

在一个 4260 条收藏、单一收藏夹的账号上完整跑过一遍：先合并去重，再按语义分成 29 个夹，最后清理失效视频。

| 阶段 | 写操作 | 失败 | B 站返回的风控码 |
|---|---:|---:|---:|
| 新建收藏夹 | 5 | 0 | 0 |
| 移动 3808 条 | 265 | 0 | 0 |
| 删除失效视频 366 条 | 19 | 0 | 0 |
| 合计 | **290** | **0** | **0** |

移动接口一次最多带 20 条资源，所以 3808 条只对应 265 次调用，不是逐条请求。

几个只有真跑到这个量级才会暴露的事实：

- **单轮 100 次写上限确实会拦人。** 一次性提交 195 次写操作被硬上限挡下，必须拆轮。这条限制不是摆设。
- **热度模型偏保守。** 热度一度报到 97/100（红区），但全程 B 站返回的风控码是 0。热度分是本工具自己的先验估计，不是 B 站的真实计数器——两者冲突时应该信错误码。热度只适合用来自适应调速，不适合当成开工门槛。
- **`media_count` 会滞后。** 批量删除后收藏夹列表仍显示旧数字（实际 0 条却报 88 条），以翻页实际拉到的条目为准。
- **有的失效视频 B 站不打标。** 标题已经是 `【已删除】`，但 `attr=0` 且未置失效位，`dead` 命令扫不到，只能点名处理。
